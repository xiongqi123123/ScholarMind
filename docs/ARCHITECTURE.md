# ScholarMind 技术架构

状态：设计已确认，第一阶段开发中。进度见 [TODO.md](TODO.md)。

## 1. 定位

自建的论文库：每天抓取 arXiv 和顶会论文，用 Agent 给每篇打标签、写分析报告。人在网页上读 PDF 和报告，AI Agent 通过 MCP 查同一份数据。

- **一个实例对应一个实验室（或一个人）**：多账号，论文和报告全员共享，个人的订阅、已读、收藏、笔记互不可见。
- **开源、自部署**：每个实验室按自己的研究方向配置数据源和标签词表。
- **真正要积累的是结构化结果**：标签和带出处的报告。PDF 随时能重新下载，不当资产存。

## 2. 总体架构

```
            arXiv API        CVF / OpenReview          (outbound via proxy)
                │                   │
                ▼                   ▼
┌─────────────────────────────────────────────────┐
│ worker processes  (same container as api)       │
│   sync ──► brief (tier 1) ──► report (tier 2)   │
│            pi, no tools       pi, no tools      │
└──────┬────────────────┬────────────────┬────────┘
       │ jobs           │ rows           │ files
       ▼                ▼                ▼
   ┌───────┐      ┌────────────┐   ┌─────────────┐
   │ Redis │      │ PostgreSQL │   │ data/ (disk)│
   │ queue │      │ truth      │   │ text, pdf   │
   └───▲───┘      └─────▲──────┘   └──────▲──────┘
       │ enqueue        │                 │
┌──────┴────────────────┴─────────────────┴───────┐
│ api  (FastAPI)                                   │
│   /       static frontend (React build)          │
│   /api    REST                                   │
│   /mcp    MCP (streamable HTTP)                  │
└───────────────▲───────────────────▲─────────────┘
                │                   │
             browser        Claude Code / Codex / pi
```

默认一个应用容器跑全部进程：接口、定时调度、1 个 `fetch` worker、若干 `analyze` worker；外加 PostgreSQL 和 Redis。任何一个进程退出，容器整体退出并由 Docker 重启。这个规模用不着拆开；镜像保留了只跑接口或只跑 worker 的启动方式，需要时可以拆成两个容器。

## 3. 组件职责

| 组件 | 职责 |
| --- | --- |
| PostgreSQL | 唯一的事实来源：论文、标签、报告、账号、个人状态。每篇论文有状态列 |
| Redis | 只做任务队列：分发、重试、并发控制。清空不丢数据，按状态列重新入队 |
| 磁盘 `data/` | 只放手动保存的 PDF（还没做）。抽出的全文文本存在数据库里，不落磁盘 |
| `worker` | 同步数据源、调用 pi 做两级分析 |
| `api` | REST、MCP、托管前端静态文件、PDF 中转 |
| pi | 唯一的模型入口，项目里不写模型客户端代码 |

Web、REST、MCP 调用同一套查询函数，只是外壳不同。

### 并行

后端按"可以并行"来写，`api` 和 `worker` 都不在进程里存状态，可以起多个进程或多个容器。

队列分两个：

- `fetch`：访问数据源（同步、下载）。只起一个 worker 串行执行，因为 arXiv 这类源有限速。
- `analyze`：简报和全文报告。起 N 个 worker 并行，N 可配，上限取决于模型接口的额度。

任务要满足三条，才能安全地并行和重试：

- **粒度小**：一个任务只处理一篇论文（简报是一批摘要），任务之间互不依赖。
- **幂等**：同一个任务跑两次，结果和跑一次一样。入库靠唯一约束加"有则更新"。
- **不重复领取**：worker 开始分析前，用一条带条件的更新把论文状态从 `queued` 改成进行中，改不成功就放弃。这样两个 worker 不会同时分析同一篇。

### 调用 pi

实测数据和完整结论见 `Temp/pi-verify/REPORT.md`（2026-11-22，pi 1.5.2）。

- **命令**：都用 `--mode json --no-session`，并关掉扩展、skills、prompt 模板、上下文文件和项目资源（`-ne -ns -np -nc -na`）。`-nc` 必须加，上下文文件不受项目信任控制。
  - 简报：`--no-tools`，摘要从 stdin 喂入。
  - 论文解读：同样是 `--no-tools`，全文从 stdin 喂入，一次调用出结果。模型的思考也计入输出上限，上限设 3.2 万以上。
- **判断成败看事件流，不看退出码**：`--mode json` 在模型调用彻底失败后退出码仍是 0。要解析最后一条消息的 `stopReason`，`error` 和 `length`（输出被截断）都算失败。
- **子进程约定**：
  - stdin 设为空设备或文件，否则 pi 会一直等输入。
  - 用独立进程组启动，超时就杀整个进程组。pi 的进程名显示为 `pi`，按命令行匹配杀不到它。
  - 只传最小环境变量（`PATH`、`HOME`、模型密钥、`PI_*`），不传数据库地址和会话密钥。
- **配置**：不用交互式登录。`PI_CODING_AGENT_DIR` 指向一个可写目录，里面的 `models.json` 写模型接口，密钥写成 `$LLM_API_KEY` 由环境变量提供。接口地址不支持环境变量，所以每次调用前按当前配置生成这个文件。接口地址、两级的模型名和密钥，管理员可以在网页上改（存在 `settings` 表，优先于 `config.yaml` 和 `LLM_API_KEY`），每个任务启动时读一次，改完从下一个任务起生效，不用重启。
- **镜像要求**：Node 22.19 以上、锁定版本的 pi；设 `PI_OFFLINE=1`。
- **多个 pi 进程可以并发**：加了 `--no-session` 后互不干扰（真实接口只测到 2 并发）。

### 成本量级

| 任务 | 模型（验证时） | 耗时 | token |
| --- | --- | --- | --- |
| 简报，20 篇一批 | `deepseek-flash` | 23–28 秒 | 约 1.2 万（每篇约 620） |
| 论文解读，每篇 | `deepseek-flash` | 80–113 秒 | 3.4 万到 6.6 万 |

正式环境从 2026-11-23 起两级都用 `glm-5.3-flash`：简报每批 20 篇要 2.5 到 3.5 分钟（`deepseek-flash` 是 30 到 40 秒），两个并发约每分钟 12 篇。

早期让模型用工具分段读全文时，同一篇论文的用量在 3 万到 108 万 token 之间波动（模型有时会自己反复读文件）。现在全文一次放进提示词，用量只取决于论文长度。

## 4. 数据流

1. **同步**：每天定时拉取配置的 arXiv 类别，按 arXiv ID、DOI、规范化标题去重入库。顶会是手动触发的批量导入，走同一套去重。
   - arXiv 用 OAI-PMH 接口，按"记录最后修改日"增量拉取。所以每天拿到的是当天有变动的论文：新论文、出了新版本的旧论文、补了 DOI 的旧论文。列表的日期筛选按首版提交日。
   - 约一成是交叉列出的论文，主类别不在配置的类别里。
   - arXiv 限速是每 3 秒一个请求、同时一个连接，所有机器合计。代码用数据库锁保证同一时刻只有一个进程在请求。
2. **简报（第一级，每一篇）**：20 条摘要一批交给 pi（不给工具），按受控词表打领域和任务标签，抽关键词，写一段总结。词表放在 system prompt 里，能命中模型接口的前缀缓存。同一批摘要跑三次，标签完全一致的只有约一半，所以人工修正标签是必要的。
3. **论文解读（第二级）**：设计见 16.1。
   - 触发：简报完成后，标签命中配置里 `analysis.report_auto` 任意一个值的论文自动排队，受每日上限约束（只计自动触发，超出的留到之后的日子补）。默认是空的，即不自动跑。任何成员都可以对某篇论文手动触发，手动的不计入上限；已有解读时重做要显式指定。
   - 过程：下载 PDF（只在内存里，不落盘；和同步共用一把锁，保证不超 arXiv 限速）→ 抽出带页码的文本存进数据库（同一篇同一版本只抽一次）→ 从 PDF 里裁出每张图和表 → 全文一次性交给模型，输出一篇 Markdown 解读。
   - 长论文：全文超过 24 万字符时，先去掉参考文献及之后的部分；还超就从最后一页往前删，并告诉模型省略了哪些。
   - 校验：非空、没有被截断、二级标题 5 到 10 个、最后一节是"存疑之处"、3000 到 10000 个汉字、裁出了图就至少引用一张图（表同理）。不合格重试一次，再失败标 `report_failed`。模型服务调用失败或下载时网络出错，放回排队下次再试。
   - 图表标记：解读里的 `[[图:Fig. 2]]` 按"类型加编号"和裁出的图表匹配，写法不同也能互认（Fig. 2、Figure 2、TABLE II、Table 2）。对上的改写成论文图注里的写法；对不上的原地换成一行说明，不影响整篇。
   - 裁图失败不影响解读，只是没有图。
   - 实测 5 篇不同类型的论文：29 个标记全部对上了图。
4. **消费**：前端和 MCP 读同一份数据。

论文状态：`new → briefing → briefed`，简报校验两次不过是 `brief_failed`。`briefing` 表示已被某个 worker 领取，超过 1 小时没完成会被重新领取。全文报告的状态单独记在 `report_status`：空 → `queued` → `reporting` → `reported` 或 `report_failed`。

## 5. 数据模型

| 表 | 内容 | 引入阶段 |
| --- | --- | --- |
| `users` | 账号、邮箱（可空、不重复）、密码哈希、角色、预设头像、订阅条件 | 1 |
| `tokens` | 个人令牌：名称、哈希、过期时间、上次使用时间；一人多个 | 1 |
| `papers` | 元数据、各来源 ID、会议、带版本号的 PDF 链接、状态 | 1 |
| `sync_state` | 每个数据源同步到哪了 | 1 |
| `tags` | 论文、类型（领域 / 任务 / 关键词，来自简报）、值、来源（AI / 人工及修改人）。标签体系的改版见 16.2 | 2 |
| `paper_texts` | 抽出的全文，按页存，同一篇同一版本一行 | 3 |
| `figures` | 解读里引用到的图和表：编号、图注、页码、图片本身、像素宽高。只存引用到的，每篇约 1MB | 7 |
| `analyses` | 只追加不覆盖：论文、级别（简报 brief、解读 report、解读后的判定 assessment）、模型、prompt 版本、JSON 结果 | 2 |
| `user_papers` | 每人每篇的收藏（`starred_at`，非空即已收藏）；已读、评分以后加列 | 已上线 |
| `collections`、`collection_papers` | 个人的收藏分组（同一人不能重名）和分组里的论文。分组是收藏的子集：放进分组会自动收藏，取消收藏会从本人的所有分组里移出；删除分组不取消收藏。别人的分组一律按不存在处理 | 已上线 |
| `notes` | 笔记，带作者，可挂在某篇论文上，仅作者可见，可以改。带划选原文（`quote`）和位置（`anchor`：PDF 页码或解读的小节）的是摘录批注；每人每篇另有一块自由笔记（`kind = page`，整块保存，清空即删除） | 4 |
| `chat_messages` | 向 Agent 提问的对话：每人每篇一段，问题和回答各一行，回答记模型、提示词版本和用量。只有本人可见，可清空 | 已上线 |
| `settings` | 管理员在网页上改过的配置：模型密钥（加密）、接口地址、模型名、提示词。没有对应的行就用部署配置和仓库里的提示词文件 | 已上线 |

解读是一篇 Markdown 文章，连同它引用的图表一起存。结构和要求见 16.1。

## 6. 账号与个人视角

- 管理员创建账号（网页「账户管理」或命令行），填用户名、邮箱、初始密码；用户名加密码登录。不开放注册，不做邮箱验证和第三方登录。
- 管理员可以在网页上改别人的角色、重置别人的密码、删除账号；不能删自己、不能撤掉自己的管理员角色，自己的密码在个人页改。删除账号会连带删掉他的令牌、收藏、分组和笔记；他改过的标签和方向留着，修改人变成空。
- 两种角色：管理员（配数据源、词表、自动分析方向、建账号）和成员。
- 每人一组订阅条件（arXiv 类别、标签、关键词），只决定各自发现页的默认过滤，不触发任何分析。
- 每人可以有多个个人令牌，供 MCP 和接口使用：一个 Agent 或一台机器一个，各自命名，可设过期时间，可单独吊销。令牌只在生成时显示一次，库里只存哈希。管理令牌和修改密码只接受网页登录，不接受令牌。
- 人工修正标签对全员生效，记录添加人。一篇论文的标签只要被人改过，之后的自动打标就不再动它的标签（只更新总结）。

## 7. 对外接口

- **REST `/api`**：前端只通过它取数据。
- **MCP `/mcp`**：
  - `search_papers`：按关键词、标签、方向、会议、日期搜索，可只看本人收藏（`starred`），可按 arXiv 的新增日筛选（`added`，日期或 `latest`；`added_kind` 区分新论文和新版本）。
  - `get_paper`：元数据、标签、报告。
  - `read_paper`：按页读原文文本。
  - `save_note`、`list_notes`、`delete_note`：笔记记在调用者名下，只有本人能读和删。网页上写的摘录批注和自由笔记也在 `list_notes` 里。
- 实现：官方 Python SDK（v2），挂在同一个应用的 `/mcp` 下，无状态、每次请求返回一个 JSON，不用 SSE。只接受个人令牌（`Authorization: Bearer`），不接受 cookie。
- `read_paper` 单次最多 10 页；库里还没有这篇的全文时会现取现抽（和同步共用 arXiv 的锁），之后直接读库。
- 比较论文、找研究空白这类事不做成工具，由调用方 Agent 用上面四个工具自己推理，避免多层 AI 总结失真。

## 前端设计方向

第一版只做骨架，细节由项目负责人亲自调。方向是：温暖的人文主义、极简手绘、抽象隐喻、不完美的几何美学。

| 维度 | 风格描述 |
| --- | --- |
| 线条 | 自然、略带手绘感，不刻意追求机械精确 |
| 形状 | 简化的几何轮廓、有机曲线、抽象造型 |
| 配色 | 奶油白、陶土橙、炭黑、鼠尾草绿、暖灰 |
| 质感 | 纸张纹理、粉彩、蜡笔、版画、轻微颗粒 |
| 构图 | 大面积留白、视觉重心集中、不对称平衡 |
| 表达 | 用简单的物体隐喻复杂概念，而非直接画出功能 |
| 气质 | 克制、温暖、聪明、安静、有一点俏皮 |

落实时的约定：

- **借鉴气质，不借用品牌**：这个方向参考了 Anthropic 的插画审美，但插画和图形都是原创，不用它的名字、logo 和专有字体。
- **视觉对齐**：所有元素对齐到同一套网格，间距用固定的刻度，不出现零散的数值。
- **少写字**：不加多余的副标题和说明文字，让布局和层级来表达。
- **动效用 Motion**，保持克制，尊重系统的"减少动态效果"设置。
- **有现成组件就用现成的**：交互件用成熟的可定制组件，自己只负责外观。
- **设计变量集中在一处**：颜色、字号、间距、圆角、动效时长都收成变量，方便调整。
- 浅色（奶油纸色）优先，深色模式暂不要求。

## 8. PDF 策略

| 场景 | 做法 |
| --- | --- |
| 所有论文 | 只存带版本号的 PDF 链接（如 `2401.12345v2`） |
| 在前端打开 | 后端从源站取回并转给浏览器，不落盘；重复打开靠浏览器缓存 |
| 全文报告 | worker 下载到内存，抽出文本存进数据库，PDF 不落盘 |
| 手动保存 | PDF 落盘，之后读本地副本，全员共享 |

- 链接带版本号是因为解读、裁出的图表和页码都对应某个固定版本。
- 中转接口只按论文 ID 取库里存的链接，不接受任意网址。
- 库里的链接取不到 PDF（会议站点返回机器人验证页或报错）而论文有 arXiv 编号时，改从 arXiv 取同一版本；解读用的全文也走这条路。两边都取不到返回 502，前端给出原始页面的链接。整次下载最多 90 秒，超时同样是 502：下载全程占着和同步共用的 arXiv 锁，不能让一个慢站点堵住后面所有请求。RSS 的站点有机器人验证，208 篇里 25 篇没有 arXiv 版本。

## 9. 配置

- `config.yaml`：数据源（arXiv 类别、顶会）、领域和任务词表、自动跑全文报告的方向、两级各用的模型、每日全文报告上限、报告语言。
- `.env`：数据库和 Redis 连接、密钥。不进仓库。

## 10. 技术选型

| 部分 | 选择 | 说明 |

| 后端 | Python + FastAPI | PDF 和 MCP 的库成熟 |

## 13. 安全

- 论文是不可信输入（已有论文在 PDF 里藏指令）。调用模型时不给任何工具，所以模型既不能执行命令，也不能读写文件；论文里的指令最多只能影响输出的文字。
- 调用 pi 时关闭扩展、MCP、skills 和项目上下文文件，只传最小环境变量。
- 所有接口都要登录或令牌。
- 管理接口（`/api/admin/users`、`/api/admin/agent`）只接受管理员的网页登录：令牌一律 403，哪怕是管理员的令牌。令牌泄露不能用来建账号或换模型密钥。
- 密钥放 `.env`。在网页上设的模型密钥用 `SECRET_KEY` 派生的密钥加密后存库，任何接口都不返回明文，只返回末四位；`SECRET_KEY` 换了就读不出来，这时退回环境变量里的密钥并记一条警告。
- 接口地址和密钥是一组连接，一起改。不填新密钥时，现有密钥只能沿用到同一主机（协议、主机、端口都相同），换主机必须给新密钥：否则管理员能把部署时配的密钥发到任意地址。探测可用模型（`POST /api/admin/agent/probe`）同样受这条约束，不跟随重定向，报错里不带对方返回的内容。

## 16. 已确认的后续设计（2026-11-23）

这一节记录和负责人逐项确认过的决定。它和前面各节冲突时，以这一节为准；对应的代码改完后再把前面的章节改过来。

### 16.1 全文报告改为"论文解读"

- **目标**：读者不看论文，只读解读，就能向别人讲清楚这篇论文。它是一个读懂了的人写的解读，不是论文的中文缩写，要有自己的概括和判断。
- **形式**：一篇 4500 到 6500 字的 Markdown 文章，6 到 9 个二级标题，标题由模型按论文内容拟，用书面的名词性标题。不再是带引句的结构化 JSON。
- **必须讲到的内容**：核心论点、领域现状和问题、切入角度、想法的来源、创新的性质、方法（围绕方法总览图）、主实验（围绕主实验表格）和关键消融、结果与作者指出的局限、解读者的理解、评价与可借鉴之处、存疑之处。
- **存疑之处单独成节放在最后**，正文正常叙述，不夹带质疑。
- **术语**：论文的专有称谓用原文，首次出现时括号里给中文解释。
- **图表**：解读里用 `[[图:Fig. 2]]`、`[[表:TABLE I]]` 这样的标记引用论文原图，编号照抄论文的写法。系统从 PDF 里把图和表裁出来，按编号替换。
- **模型和调用方式**：用 `deepseek-flash`。全文一次性放进提示词，不再用只读工具分段读（40 页的论文约 4.3 万 token）。模型的思考也计入输出上限，上限至少设 3.2 万。实测每篇 2.5 万到 6.3 万 token，一到两分钟。
- **提示词**定稿前的版本在 [design/report-prompt-draft.md](design/report-prompt-draft.md)。在三个模型上对比过（flash、pro、Sonnet），水平接近，所以用最便宜的。
- 原来的引句三步核对随结构化 JSON 一起退出。

### 16.2 标签体系

| 标签 | 取值 | 怎么得到 | 覆盖范围 |
| --- | --- | --- | --- |
| 来源 | `arXiv` 或会议名 | 数据源自带 | 全部 |
| 年份 | 会议论文取会议年份，纯 arXiv 论文取首次提交年份 | 数据源自带 | 全部 |
| 领域 | 固定 5 个：计算机视觉、自然语言处理、机器人、具身智能、自动驾驶；另有"范围外"。每篇 1 到 2 个 | 模型读摘要 | 全部 |
| 方向 | 领域下的研究方向，如 3D Gaussian Splatting。每篇 1 到 3 个 | 模型读摘要 | 全部 |
| 论文类型 | 方法、数据集、基准、综述、理论、实证分析、系统 | 模型读摘要 | 全部 |
| 创新性质 | 机制创新、模块组合、方法迁移、系统集成、新问题或新设定 | 模型读全文 | 有解读的论文 |
| 关键词 | 自由填写，3 到 6 个 | 模型读摘要 | 全部 |

- **来源的规则**：arXiv 是基础；同一篇论文一旦出现在某个会议的论文集里，来源就变成那个会议，年份变成会议年份。arXiv 编号保留在后台。
- **范围外的论文**照常入库，标成"范围外"，默认不显示，不做解读。
- **质量打分不做**（2026-11-23 决定）。原方案是四个维度各 1 到 5 级加三档总评，测了稳定性（10 篇，每篇 4 次，全文输入）：总评 9/10 篇一致，各维度最多差 1 级，但创新性 30 次里 26 次给 3，没有区分度，实用价值有一半论文在相邻两档之间跳；样本小，也没有和人工评价对照。数据在 `Temp/stage8-assess/`。
- **创新性质**保留：解读保存后，在同一个任务里用全文再调一次模型（`prompts/assess.v3.md`），输出五类之一和一两句理由，存成 `analyses` 里的 assessment 记录，`papers.innovation` 跟着最新一次，用于筛选。它不在 `tags` 表里，不能手工编辑。失败不影响解读。三次重复的一致率约 70%，混淆集中在"模块组合"和"系统集成"之间；提示词里写了两者的分界（贡献能否脱离整个系统单独拿走）。每篇约 1 万到 5 万 token。`scholarmind assess` 给已有的解读补跑。
- **封面图**（列表里的 `cover`）：同一次调用还让模型给出方法总览图的编号，对上解读引用的图就标为封面（`figures.cover`）；没有标注时取图注含 overview、framework、architecture、pipeline 等词的图，再没有就取第一个被引用的图。表格不当封面。11 篇的核对里，有总览图的 9 篇全部选对。

### 16.3 方向词表：先定一套，不够再自建

- 起步词表内置在 `backend/scholarmind/vocabulary.yaml`，5 个领域共 88 个方向（[design/vocabulary-draft.yaml](design/vocabulary-draft.yaml) 是最初的 68 个方向的草稿）。每个方向有英文规范名、中文说明、别名和一句英文定义；定义里写明相邻方向怎么分。`config.yaml` 里写了 `vocabulary` 就用它替换内置的。
- 方向的粒度是"有一批人专门在做、能叫得出名字的研究方向"。更细的具体方法名进关键词。
- 模型打标时先在词表里选；都不合适才新建。新建时必须给出英文名、一句话定义、所属领域。
- 入库前查重：名字规范化后（忽略大小写、空格、连字符和复数的 s）和已有的名字、别名比对，对上就用已有的。写词表时持有同一把数据库锁，多个 worker 同时新建同名方向也只会有一条。
- 新建的方向立刻生效，标记为自建。
- 标签存的是方向的编号，不是文字，所以改名和合并不用重新给论文打标。
- **每周的整理任务**：一个定时的 Agent 只筛查自建的方向，判断它是不是已有方向被意外地重复新建了；是就合并到已有的方向上。它不能改动起步词表里的方向。合并要留记录（`topic_merges` 表）；被合并方向的名字变成目标方向的别名，以后再用这个名字会落到目标上。接口（管理员）：`GET /api/admin/topics`、`POST /api/admin/topics/{topic_id}/merge`、`GET /api/admin/topic-merges`。
- **实测**（240 篇，`deepseek-flash`）：每批 20 篇约 1.7 万 token；新建方向 2 个；判为范围外的约 7%。范围外的标准是论文的主要贡献不在五个领域之内，机器人本体和语言模型本身始终算在范围内。

### 16.4 顶会来源

- 接 13 个会议的主会论文：NeurIPS、ICML、ICLR、ICRA、IROS、RSS、ECCV、ICCV、CVPR、ACL、AAAI、EMNLP、ACM MM。KDD 不接（基本都在范围外）。
- 范围是最近五年（2022 年起，2026-11-23 改定；最初定的是只拿最新一届）。逐届核实过：54 届可用，共约 10.6 万篇。拿不到的：ICLR 2022、2023（官方论文集站点只从 2024 年起，OpenReview 拦匿名访问）；NeurIPS 2025、ECCV 2026、IROS 2026 还没放出来，放出来后自动接上。
- 调研结论和各会议的细节在 [design/conference-sources.md](design/conference-sources.md)。四个适配器：
  - OpenAlex：ICRA、IROS、ACM MM、AAAI、ACL、EMNLP、RSS。
  - CVF 开放获取站：CVPR、ICCV、ECCV。
  - 官方论文集站点：NeurIPS、ICLR。
  - PMLR：ICML。
- 口径：只收主会研究论文（长文和短文都算）；Findings、workshop、demo、工业分轨、立场论文、数据集与基准分轨都不收。
- 不申请 OpenReview 账号，不用 IEEE 的官方接口，OpenAlex 用免费额度。
- IEEE 和 ACM 的会议（ICRA、IROS、ACM MM）PDF 不开放，约一半论文在 arXiv 上有对应版本。没有 arXiv 版本的只做简报，不做解读。
- ECCV 2026 等开放获取版上线再收；NeurIPS 2025 等官方索引页补全再收。
- 会议版和 arXiv 版合并时，更新原来那一行，不换行：标题、摘要、作者、DOI、来源、年份、分轨以会议版为准；arXiv 编号、版本、分类、日期以 arXiv 为准；收藏、方向、标签、笔记、解读都留在原行上。PDF 用会议版（开放获取时），否则用 arXiv 版；已有解读的论文保留解读生成时的 PDF。
- 合并规则偏保守：arXiv 编号相同直接合并；DOI 相同合并；只有标题相同时，要求库里只有一篇这个标题、双方不都是会议条目、作者按姓氏重合过半。
- **实现**（`venues.py`，迁移 0009）：`papers` 加 `source`（默认 arXiv）、`year`、`track`、`venue_key`。
  - 手动导入一届：`scholarmind import-venue CVPR 2026`；批量：`scholarmind import-venues --since 2022`，新届次在前，一届做完再排下一届。
  - 导入任务在 fetch 队列里分段跑，每段最多 10 分钟，每天的 arXiv 同步可以插在中间。逐篇请求的站点间隔 2 秒，实测每篇约 5 秒，五年全部导入约 60 小时。
  - 单次请求失败最多试 5 次（间隔 30、60、120、240 秒，429 和 503 按 `Retry-After`，最长 10 分钟）；一届出错就跳过，继续后面的届次。
  - 应用重启会打断导入，重启后要再跑一次 `import-venues`：做完的届次跳过，做到一半的从断点继续。
  - 每个会议的第一届要手动导入；之后每周检查一次（`sync.venues_cron`，默认周一 04:00），有更新的届次就自动导入，最新一届导入后 6 周内每周补跑。库里一届都没有的会议不会自动导入任何东西。
  - `--no-briefs` 把导入的论文标成 `held`，不进简报；`scholarmind release-held` 放回。
  - 每届有保护：篇数少于 `min_papers`、或摘要和作者的覆盖率低于一半，就判为失败，不入库（多半是站点改版了）。
  - 会议论文没有 `added_on`，不出现在每日新增里。
- 接口：每篇带 `source`、`year`、`track`；列表的 `source`、`year` 可多选，facets 里有这两组；`GET /api/sources` 给出来源和年份的组合及篇数。

### 16.5 每日新增

- "某天的新增"按 arXiv 的日期算，不按入库时间：OAI-PMH 每条记录的 datestamp 是 arXiv 公布这次变动的日子，存进 `papers.added_on`。
- 两类都算：首次公布的新论文（`added_kind` 为 `new`，即版本号是 1），和出了新版本的旧论文（`updated`）。
- 只改元数据的不算：记录的最新版本比 datestamp 早 7 天以上时（正常间隔 1 到 4 天），这次变动是补 DOI、改分类之类，不写 `added_on`，原来的日子保持不变。
- arXiv 只给每条记录最后一次的 datestamp，所以一篇论文再出新版本时会从原来那天挪到新的那天；要保留完整历史得另建按版本的表，目前没做。
- 顶会导入的论文没有 `added_on`，不出现在每日新增里。
- 接口：`GET /api/papers?added=<日期>|latest`（响应带 `added_day`、`pending`、`failed`，后两个是那一天还没做完和做失败简报的篇数）、`added_kind=new|updated`、`GET /api/papers/added-days`。篇数和列表一样默认不含范围外的论文。
- 已有数据补 `added_on`：`scholarmind sync --from <第一次同步的起始日> --until <今天>`（补数据模式，不动同步进度）。起始日不要往前多放，范围内库里没有的记录会被当成新论文入库并排上简报。

### 16.6 手动解读：插队、进度、失败原因

- 成员在网页上点的解读（`report_trigger = manual`）进单独的 `manual` 队列，analyze worker 先取它再取 `analyze`，所以不排在打标批次和自动解读后面；worker 手上的那一批打标要先跑完，最多等几分钟。重新入队时手动的回到 `manual`。
- 进度存在 `papers` 上（`report_stage`、`report_stage_at`），不放 Redis：取 PDF 和文本（`pdf`）→ 裁图表（`figures`）→ 模型撰写含重试（`writing`）→ 匹配图表并保存（`checking`）。`GET /api/papers/{id}` 返回 `report_progress`：阶段、阶段开始时间、前面还有几篇手动解读（只对手动的算，不含正在跑的）、预计剩余秒数、通常耗时（最近 10 篇解读从领取到保存的中位数）。这个接口会被页面轮询，每次最多多两条查询，不读队列。
- 失败原因存 `papers.report_error`（`code` 加英文 `detail`）：`no_pdf`、`no_text`、`pdf_unreadable`、`invalid_answer`、`cut_off`；手动解读另有 `network`（下载时网络出错）和 `model_error`（模型服务调用失败），直接标失败让人重点，自动解读遇到这两种仍放回排队等每日任务重试。

### 16.7 向 Agent 提问

- 阅读页上对一篇论文提问，每人每篇一段对话（`chat_messages`），可清空。接口：`GET/POST/DELETE /api/papers/{id}/chat`。
- 模型拿到的内容：论文全文（按页，库里没有就像解读那样现取现抽）、最新的解读、对话里最新的 20 条（且不超过 4 万字符）、提问时划选的原文。不给任何工具。用解读的模型；提示词 `prompts/chat.v1.md`，管理员可在网页上改，要求只依据论文回答、论文没讲就直说、用 `[p.3]` 标页码。
- 在 api 进程里直接调 pi，不走队列：提问不能排在打标批次后面。回答边写边用 SSE 推给页面（`delta`、`done`、`error`）；pi 内部重试时文本会重来，以 `done` 里的全文为准。
- 限制：一个进程里同时最多 2 个回答在写（每个 pi 进程约 150 MB，小内存的机器上不能放开），第三个返回 503；同一人同一篇同时只能有一个，靠一把会话级的 advisory lock，进程崩溃或重启时自动释放；单个回答 180 秒超时。
- 问题和回答在回答完成时一起入库，失败或中断什么都不存。

### 16.8 摘要的逐句中译

- 详情页在英文摘要旁显示逐句忠实的中译（`abstract_zh`），不再显示打标时写的概要；概要是模型自己的归纳，和原文对不上句子，只留在列表卡片上。
- 第一次打开论文时才翻译并存下来（`POST /api/papers/{id}/abstract-zh`），不回填、不并进打标批次：库里十万篇里绝大多数不会被打开。之后 `GET /api/papers/{id}` 直接带出。
- 译文存成 `analyses` 里的一行（级别 `translation`），连同所译摘要的哈希；摘要变了（arXiv 新版本、会议版合并）哈希对不上，旧译文不再返回，下次打开重翻。
- 在 api 进程里调 pi，用打标的模型；同时最多 2 个，和问答的名额分开；同一篇同时只翻一次。只做轻量检查：非空、没被截断、段数和原文一致，重试一次后放弃。提示词 `prompts/translate.v1.md`，管理员可改。
- 实测 `glm-5.3-flash` 每篇约 20 秒、2 千 token。
